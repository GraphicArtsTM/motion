# DECISIONS — решения, принятые при реализации ТЗ v6.0

Формат: что было неясно или противоречиво → что выбрано → почему. Нумерация сквозная.

## Архитектура и стек

**D-01. Размещение и пакет.** Проект лежит в каталоге `taxopark-referral-bot/` репозитория; `src` — Python-пакет
(импорты `from src.core…`), что буквально повторяет структуру п. 13.2 и исключает конфликты имён
(`core`, `db`, `admin` слишком общие для пакетов верхнего уровня).

**D-20. Локализация.** Fluent подключён через `fluent.runtime` напрямую (`src/bot/i18n.py`), без middleware
`aiogram-i18n`: язык берётся из `users.language`, а тексты нужны и вне апдейтов (диспетчер outbox, воркеры).
В коде ключи пишутся через точку (`wallet.title`), в `.ftl` — через дефис (`wallet-title`): идентификаторы Fluent
не допускают точек. Узбекская кириллица генерируется из латиницы скриптом `scripts/translit_uz.py` (правила
транслитерации + защита плейсхолдеров, HTML и брендов). **Перед запуском тексты должен вычитать носитель языка.**

**D-21. Админ-UI.** SQLAdmin подключён только для просмотра таблиц (read-only, экспорт). Все изменения —
через JSON admin API (`src/admin/api.py`) и Telegram-админку, которые вызывают ядро, — так бизнес-логика не
дублируется в формах SQLAdmin (R6). React-фронтенд не входит в поставку; Postman-коллекция описывает все действия.

**D-22. Python 3.12 в Docker** (ТЗ: 3.11+). Код совместим с 3.11.

**D-23. Тесты.** Используется настоящий PostgreSQL (миграции Alembic + сиды на каждый тест, TRUNCATE между
тестами), а не testcontainers — в среде разработки не было Docker. В CI PostgreSQL поднимается сервисом GitHub
Actions. factory-boy заменён простыми фабриками `tests/factories.py` (асинхронный SQLAlchemy).

**D-32. Rate limiting бота** — в памяти процесса (`ThrottlingMiddleware`), не в Redis: на один процесс достаточно,
а апдейты конкретного пользователя Telegram доставляет последовательно.

## Схема БД (дополнения к Разделу 10)

Таблицы раздела 10 созданы буквально (миграция `0001`), порядок по зависимостям, круговые связи
`accruals → withdrawals` и `user_milestones → accruals` вынесены в `ALTER TABLE` (E1). Дополнения:

**D-05. `notification_outbox`.** Ядро не зависит от Telegram: уведомление пишется в outbox в той же транзакции,
что и бизнес-изменение (нет «денег без уведомления» и «уведомления без денег»), а диспетчер бота доставляет его
с лимитом скорости, ретраями и обработкой блокировки бота пользователем. Параметры типизированы
(`{"__money__": …}`, `{"__dt__": …}`, `{"__t__": key}`) и форматируются на языке получателя.

**D-06. `sync_cursors`** — курсор синхронизации заказов (`get_sync_cursor("orders")` из A13).

**D-07. `admin_credentials`** — логин, хеш пароля (scrypt), секрет TOTP для веб-панели (2FA от роли admin).

**D-08. `user_notes`** — заметки к карточке водителя. **D-09. `fraud_whitelist`** — белый список антифрода.

**D-10. Колонки:** `users.bot_blocked`, `accruals.parent_accrual_id` (дробление начислений, D-02),
`fraud_flags.period_id` (идемпотентность правил по периоду), `support_tickets.admin_message_id/admin_thread_id`
(ответ оператора reply-сообщением), `broadcast_recipients.outbox_id` (статистика рассылки).

**D-11. Неизменяемый audit log** (14.2 п.10) — триггер запрещает UPDATE/DELETE строк `audit_log`.

## Деньги

**D-02. Модель кошелька.** Инвариант: `users.balance_available == Σ accruals(status='available') ==
SUM(wallet_ledger.amount)`. Чтобы он держался при выводе произвольной суммы, частичном списании и погашении
долга, начисление **дробится**: от него отделяется часть с новым статусом (`parent_accrual_id`, ключ
`split:<id>:<n>`). Часть начисления, ушедшая на погашение долга, получает статус `cancelled` с комментарием
`debt_repayment` — она считается «выплаченной» в A17 и в лимите welcome-бонуса, но не входит в «Всего заработано»
(иначе заработок был бы посчитан дважды: переплата уже выведена). Положительная корректировка оформляется
начислением типа `manual` (сначала гасит долг). Инвариант `Σ withdrawals(completed) = Σ accruals(withdrawn)`
выполняется точно благодаря дроблению.

**D-24. SAVEPOINT вместо ROLLBACK в ядре.** `request_withdrawal` выполняет проверки и резерв внутри
`begin_nested()`: при отказе откатывается только операция вывода и её `FOR UPDATE`, а объекты вызывающего кода
(бот, API) не «протухают». Остальные функции ядра не делают `rollback()`.

**D-25. Возврат при неудачном выводе гасит долг.** Если за время обработки вывода появился долг (пересчёт),
возвращённые деньги сначала гасят его (`settle_debt_from_balance`). Деньги не теряются (R15).

**D-26. Зависший `processing`** (воркер упал во время вызова API) не повторяется вслепую: переводится в
`verifying` и сверяется (статус транзакции → поиск по метке). Зависший `pending` (потеряна задача) ставится в
очередь заново с тем же `idempotency_token`. Задачи ARQ имеют `job_id = имя + аргументы` (без дублей).

**D-27. Лимит на реферера** (`max_payout_per_referrer_per_month`) — начисление сверх лимита не создаётся
(буквально по A6), а бюджет программы (`monthly_program_budget`) переводит начисления в `hold` (2.10).

**D-28. Описание транзакции Fleet** = настройка `payout_description` + метка `REFBOT-W{id}` (R9 — тексты не в коде).

**D-29. Провайдеры `csv`/`manual`** не умеют выплачивать — все выводы идут в `awaiting_approval` с ручной выплатой.

## Бизнес-правила

**D-03. Границы периода** — `[начало, конец)`: `ended_at >= starts_at AND ended_at < ends_at`, `ends_at` — 00:00
первого числа следующего месяца по Asia/Tashkent. `BETWEEN` из A5 посчитал бы заказ ровно в полночь в двух
месяцах.

**D-04. REHIRE.** Таблица 3.3 (раздел 3, высший приоритет) и код A2 расходятся: по 3.3 водитель, работавший в
парке в последние 90 дней, получает доступ сразу, рефералка не засчитывается, админу уведомление; по A2 — идёт на
модерацию. Реализовано по разделу 3. Проверяются **все** профили с тем же телефоном/ВУ (при повторном найме Fleet
может создать новый профиль, а `fire_date` стоит на старом).

**D-12. Антифрод внутри закрытия периода.** Правила прогоняются в `close_period` после подсчёта баллов и **до**
начислений: открытый флаг переводит новое начисление в `hold` (A8), критический флаг сразу делает реферала
`fraud`. Задача `fraud_check` (1-го, 03:00) применяет реакции: 30–69 — `hold`, 70–99 — `cancelled` + задача
модератору. Иначе начисление по подозрительному рефералу было бы доступно к выводу целый час.

**D-16. IMPOSSIBLE_HOURS только при наличии данных о времени на линии.** «Нет строк в `driver_online_time` за
период» означает, что синхронизация не работала, а не «0 часов на линии» — иначе сбой API превращал бы всех
рефералов во фрод. При наличии данных (в т.ч. нулевых) работает формула E7. Сравнение целочисленное:
`points_x100 × 3600 > limit × 100 × online_seconds`.

**D-17. Низкий риск (< `fraud_autoapprove_below`)** — флаги автоматически закрываются, чтобы A8 не держал
начисления в `hold` по правилам весом 10–20 баллов.

**D-13. Лимит welcome-бонуса в A17.** Код A17 не проверяет `referred_bonus_max_periods`; при доначислении лимит
учитывается так же, как в A6, иначе пересчёт мог бы выплатить второй «первый» бонус.

**D-14. Категория авто для уровня 2 определения тарифа** — если у авто несколько категорий, грузовая
приоритетна, иначе первая. Сопоставление кодов Fleet с кодами справочника — настройка `tariff_aliases`.

**D-19. Текст условий с плейсхолдерами** (`{threshold}`, `{bonus}`, `{coefficients_table}`, …): суммы и таблица
подставляются из справочников при показе (R3). Версия условий и время приёма фиксируются в
`user_terms_acceptance`; при изменении правил публикуется новая версия.

**D-33/34. Гейты доступа.** `rejected` видит экран отказа и поддержку (3.7); заблокированный — только экран
блокировки. Без приёма актуальных условий закрыты кошелёк, вывод, ссылка, промо-материалы и оспаривание
(2.13); прогресс, друзья и рейтинг доступны. Логика — в `core/onboarding/access.py`, применяет её middleware.

**D-37. Уведомления о прогрессе.** Порог 50/80/90% отправляется один раз за период на уровень и не чаще раза в
сутки по другу (A18). «Дедлайн вытесняет пороговое» (TC-92) реализовано так: если сегодня выполняется условие
дедлайна, пороговое уведомление не отправляется (задача прогресса идёт в 10:00, дедлайн — в 11:00).
Пользователь может выключить уведомления о прогрессе друзей в «⚙️ Настройках».

**D-38. Ежемесячный дайджест** — всем подтверждённым водителям 1-го числа: месяц и число их друзей, выполнивших
план (итоги с суммами реферер получает отдельно при закрытии периода).

**D-30. Дубликаты телефона** проверяются дважды: при получении контакта (сразу понятная ошибка) и при
завершении регистрации (гонка двух регистраций).

## Интеграция с Fleet

**D-35. Шаг 0 не выполнен.** Доступа к реальному парку (ключи API) у разработки не было. Пути и поля методов
собраны в одном месте (`ENDPOINTS` и функции `_map_*` в `src/integrations/fleet/api.py`) по публичной
документации и помечены в `API_SCHEMA.md` как «не подтверждено». Скрипт `scripts/api_recon.py` выполняет Шаг 0 и
печатает сводку «есть / нет». **До запуска в продакшен его нужно прогнать и при расхождениях поправить mapping.**

**D-15. Пагинация заказов.** Метод списка заказов Fleet использует курсор, а A13 описан через `offset`.
`ApiFleetProvider.list_orders(limit, offset)` хранит курсоры по смещениям, интерфейс A13 сохранён. Обе
синхронизации защищены от бесконечного цикла (повтор страницы → стоп).

**D-36. Фото ВУ** хранятся как Telegram `file_id`; открытие фото модератором пишется в audit log.

## Производительность

**D-39. Нагрузка (TC-110).** 200 одновременно активных пользователей (по 3 действия с паузами 1–3 с): p95
0,55 с на одном процессе. Экстремальный «залп» из 200 апдейтов в одну миллисекунду: p95 1,8 с на одном процессе,
поэтому веб запускается с 2 воркерами uvicorn, а вебхук — с `max_connections=40`. Нагрузочный тест —
`RUN_LOAD=1 pytest tests/e2e/test_load.py -s`.

**D-40. Гонка создания периода** (найдена нагрузочным тестом): параллельные апдейты на стыке месяцев создавали
период дважды. `open_period` использует `INSERT … ON CONFLICT DO NOTHING` и снимок под `FOR UPDATE`.

## Запуск и настройка

**D-41. Запуск в один клик (Windows).** `start.bat` проверяет и при необходимости запускает Docker Desktop, при
первом запуске открывает мастер настройки, затем `docker compose up -d --build`, ждёт `/health` и открывает
страницу состояния. Docker выбран вместо «голого» Python на Windows: PostgreSQL и Redis не ставятся на Windows одной
кнопкой, а образ одинаков для компьютера и сервера.

**D-42. Мастер настройки** (`src/setup_wizard`) — локальная веб-страница в отдельном контейнере (`setup`),
доступна только с этого компьютера (127.0.0.1:8765). Пишет `.env` и `config/initial_settings.json`; настройки из БД
(контакты парка, режим вывода, категория транзакций, учётная запись панели) применяются сервисом `migrate` один раз
(`src/bootstrap.py`), после чего хеш пароля и секрет 2FA удаляются из файла. Пароль БД при повторной настройке
не меняется (том PostgreSQL уже инициализирован с ним). Пустые поля секретов означают «оставить прежние».

**D-43. Два режима бота.** `BOT_MODE=polling` — бот работает отдельным сервисом и сам опрашивает Telegram (домен не
нужен); `webhook` — бот внутри веб-процесса, nginx + Let's Encrypt. Профили docker compose (`COMPOSE_PROFILES`)
включают нужные сервисы.

**D-44. Проверка доступов ключа Fleet без изменений в парке:** чтение с limit=1, методы с параметром — с
несуществующим ID (400/404 = доступ есть), создание транзакции — заведомо неверным запросом с суммой 0.
Без доступа к созданию транзакций мастер включает ручной вывод.

**D-45. Запуск без Docker (основной для Windows).** `start.bat` → `scripts/windows/local.ps1`: `uv` ставит
портативный Python 3.12 и venv, портативный PostgreSQL 16 (официальные сборки EnterpriseDB) запускается из
`runtime\` на 127.0.0.1:54329. Всё работает одним процессом `python -m src.local` (веб, бот polling, очередь,
планировщик) с перезапуском упавших частей. Redis заменён: очередь задач — таблица `task_queue`
(`QUEUE_BACKEND=db`, частичный уникальный индекс по `job_key` вместо `_job_id` ARQ, `FOR UPDATE SKIP LOCKED`),
расписание — встроенный планировщик по тому же `JOB_SCHEDULE`, состояние диалогов aiogram — таблица `fsm_storage`.
Задачи — те же функции, что у воркера ARQ, с блокировками `job_locks`. Docker-режим сохранён (`docker\`, `*.sh`).

**D-46. Библиотеки Visual C++** берутся из архива PostgreSQL (каталог pgAdmin), чтобы обычно не требовать установки
VC++ Runtime с правами администратора; если их не хватает — ставится официальный `vc_redist.x64.exe` (Windows
спросит разрешение).

**D-47. Кириллица в пути.** PostgreSQL на Windows ненадёжно работает с не-ASCII путями к данным — в этом случае
`runtime` размещается в `C:\TaxoparkBot\runtime`.

**D-48. Скрипты Windows.** `.bat`-файлы в корне — только ASCII (нет проблем с кодовыми страницами `cmd`), все тексты на
русском — в `local.ps1` (UTF-8 с BOM, иначе Windows PowerShell 5.1 читает его как ANSI). `$ErrorActionPreference =
'Continue'` с явной проверкой кодов возврата: в PS 5.1 строка в stderr у psql/initdb при `Stop` обрывает скрипт.
